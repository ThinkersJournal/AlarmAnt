kind: **BREAKING**: the Android app accepts only `https://` enrolment links; the server can serve HTTPS; re-enrolling voids the replaced phone's ack tokens
---
Three changes on one branch. (1) `register()` also voids the ack token of the device it replaces, on every in-flight alert, exactly as `revoke` does (PM ruling 2026-11-19, option a); server-side only, nothing sent to the old phone, nothing restored, a first enrolment voids nothing. Test written first and seen failing; a sabotage check (voiding the new token instead) fails it. `RegisterConfig` gains `alerts`. (2) `Registration.parseLink` rejects `http://` (the enrolment code, FCM token and lifelong ack token must not cross a network in the clear; the manifest already forbids cleartext). Phone side only; the Kotlin unit tests were NOT run here (no JDK): the changed `parseLink` assertions (https accepted, `http://h&c=abc` rejected) were exercised only by CI. (3) `alarmant serve` serves HTTPS when `ALARMANT_TLS_CERT_FILE` and `ALARMANT_TLS_KEY_FILE` (PEM, both or neither) are set; neither keeps plain HTTP for use behind a proxy; errors are fixed text, never key material. `httpant-server` and `httpant-client` move to 0.7.10 (server with its `tls` feature); `rcgen` 0.14.10 is a dev-dependency. Verified: 190 Rust tests pass (new TLS tests: both-or-neither, matching pair, mismatched key refused, missing files, listener binds), clippy clean, `cargo deny` ok. Not run: a live TLS handshake, a phone, Firebase.
