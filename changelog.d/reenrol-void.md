kind: **BREAKING**: the Android app accepts only `https://` enrolment links; the server can serve HTTPS; re-enrolling voids the replaced phone's ack tokens
---
Three changes on one branch. (1) `register()` also voids the ack token of the device it replaces, on every in-flight alert, exactly as `revoke` does (PM ruling 2026-11-19, option a); server-side only, nothing sent to the old phone, nothing restored, a first enrolment voids nothing. Test written first and seen failing; a sabotage check (voiding the new token instead) fails it. `RegisterConfig` gains `alerts`. (2) `Registration.parseLink` rejects `http://` (the enrolment code, FCM token and lifelong ack token must not cross a network in the clear; the manifest already forbids cleartext). Phone side only; the Kotlin unit tests were NOT run here (no JDK): the changed `parseLink` assertions (https accepted, `http://h&c=abc` rejected) were exercised only by CI. (3) `alarmant serve` serves HTTPS when `ALARMANT_TLS_CERT_FILE` and `ALARMANT_TLS_KEY_FILE` (PEM, both or neither) are set; neither keeps plain HTTP for use behind a proxy; errors are fixed text, never key material. `httpant-server` and `httpant-client` move to 0.7.10 (server with its `tls` feature); `rcgen` 0.14.10 is a dependency. (4) A home LAN without a public certificate: `ALARMANT_TLS_SELF_SIGNED_NAMES` (IPs and host names) makes a self-signed pair once in `ALARMANT_DATA_DIR` (key created exclusively, mode 0600 on Unix), reused afterwards; `alarmant enroll` with `ALARMANT_PUBLIC_URL` prints the full link, carrying `f=<SHA-256 of the certificate>`. The phone (new `PinnedTls`, the only custom trust code in the app) accepts only a certificate whose SHA-256 equals `f=` for the enrol, token-update and ack connections, keeps the default hostname verifier, and uses the system trust store when the link has no `f=`; a malformed `f=` rejects the link. Patent reading `PATENT-TLS-PIN-READING.md` (US2018/0302787, US9930028, US11451535, US2020/0396610: all outside as read). Verified: 194 Rust tests pass (new: fingerprint, self-signed made once and reused with an IP SAN, half-a-pair and no-name refused, link encoding, plus the TLS tests above), clippy clean, `cargo deny` ok. Kotlin unit tests were NOT run here (no JDK); only CI exercises `PinnedTlsTest` (right fingerprint accepted, wrong fingerprint refused, another valid certificate's fingerprint refused, bad pin forms refused, no pin keeps the default socket factory, a pin gets its own factory and leaves the default untouched) and the new `RegistrationTest` pin assertions. Not run: a live TLS handshake from the phone, a phone, Firebase.
