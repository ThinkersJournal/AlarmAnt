kind: **BREAKING**: `POST /alert` answers 429 above 6 alerts an hour or 20 a day per key (settable)
---
ROADMAP A10 (opened 2026-11-20 by pm-ants): the endpoint had no rate or count limit, so any holder of the API key could raise alerts without bound. A new `ratelimit` module counts raised alerts per key **owner** over a rolling hour and a rolling day (defaults 6 and 20; `ALARMANT_RATE_PER_HOUR` and `ALARMANT_RATE_PER_DAY` change them, a non-number or 0 refuses to start). The check runs after authentication: a wrong key is the usual 401 and spends nothing; an over-limit alert answers `429 {"error":"too many alerts; try again later"}`, sends **no push**, is not counted (being refused does not extend the wait) and is noted on stderr without any text. Owners, not keys: there is one API key today, so one owner; keys of one sender must name the same owner when more keys exist, so a second key cannot double the budget (tested at the limiter). Counts are in memory, so a restart forgets them. Red first: the new serve test failed with 202 where 429 was expected against a limiter stub that allowed everything, and a sabotage (`>` for `>=`) fails five tests. 206 Rust tests pass, fmt, clippy and `cargo deny` clean. A sender that raises more than 6 an hour will now be refused: breaking for such a caller, hence the major bump pre-1.0. Not run: a live server.
